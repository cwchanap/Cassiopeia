# HPA-1311 — Enemy AI for Turn-Based Battles (Design Spec)

**Linear:** [HPA-1311](https://linear.app/cwchanap/issue/HPA-1311/enemy-ai-for-turn-based-battles)  
**Base:** `main` at `cf7c52942251e2046d3d926c03e406d76d3ad98b` (HPA-1310 / PR #6 merged).  
**Delivery:** One draft PR for design, implementation, tests and acceptance evidence.

## Goal and boundaries

Give a computer-controlled fighter one deterministic turn of legal battle commands. Three
data-defined archetypes ship: Aggressor closes and targets the weakest opponent it can
profitably hit; Marksman prefers standoff distance and avoids adjacent opponents; Guardian
stays near an encounter-authored post, Guards frequently and punishes approaching opponents.
The same planner can control the squad in a headless integration test.

The battle engine remains the sole rules authority. No live game integration, renderer,
HUD, animation, save change, encounter content, art, audio, difficulty, tactical lookahead
or per-encounter scripts. HPA-1315 owns the playable spar and its runtime scheduling.
Do not add an AI framework, a dependency, a separate battle-state model or an asynchronous
worker. Do not redesign the existing reducer.

## Current code and public contract

`src/lib/game/simulation/battle/index.ts` already exports `createBattle`,
`getTurnOrder`, `getReachableCells`, `getMoveTargets`, `applyBattleCommand`,
`forecastMove`, `legalAimCells`, `affectedCells`, `cellDistance` and the
catalogs. `BattleState` contains `hasMoved`, `hasActed`, `outcome`, initiative,
fighters and terrain. Commands return a fresh state and ordered events on acceptance.

Add `ai.ts` (planner and score helpers), extend `content.ts` with the readonly
archetype weight catalog, and add these small public contracts to `types.ts`/the barrel:

```ts
type AiArchetypeId = 'aggressor' | 'marksman' | 'guardian';
type BattleAiProfile =
	| { archetype: 'aggressor' | 'marksman' }
	| { archetype: 'guardian'; post: Cell };

function planBattleTurn(
	state: BattleState,
	actorId: string,
	profile: BattleAiProfile
): BattleCommand[];
```

The caller owns profile assignment; do not put AI configuration in BattleState,
FighterTemplate or the save. The guardian post is required and must be a valid standable
integer cell on the map; fail clearly for invalid authored configuration, not silently
invent a post. The planner accepts the active fighter of either side; return an empty
array for terminal state, a dead/unknown actor or a non-active actor. A normal result
contains optional move, one action and endTurn with final facing, except when the
action itself ends the battle or kills the actor and hands off. A partially completed
active turn is supported: after movement, omit movement; after action, only choose
endTurn. The input state and profile must remain unchanged, and returned commands must
own their coordinates rather than aliasing the input. No mutation, wall clock or
randomness in the planner. It returns commands, not events or a new authoritative state.

The future runtime can plan once at turn start and feed each command to the existing
reducer in order, playing the returned events before sending the next. If the authoritative
state changes unexpectedly, discard the pending sequence and replan only for the
current active fighter. This ticket does not implement that runtime.

## Enumerating a turn

1. Check `getTurnOrder(state).activeId` and outcome. Include the current cell once
   (no move command); enumerate every other legal cell from `getReachableCells(state)`
   without an explicit fighter ID. The explicit-ID overload is a geometry query that
   ignores the active turn's phase; it is for threat estimates, not movement permission.
2. For each cell, apply the actual move command once to obtain a speculative state, or
   use the input state for staying. Never relocate fighters by writing into a shallow
   copy or recompute path costs. Rejecting an allegedly legal move is a regression, not
   an alternative rules path.
3. In that state, enumerate all owned move slots in basic/technique/finisher order.
   `getMoveTargets` already filters ownership, qi and valid aims with living hostile
   targets, including line/arc multi-target hits. Consider every returned aim, plus
   Guard and Gather qi even at full qi (legal but gains zero). Enemy fighters cannot
   use the shared squad bag. For the squad-side test controller use the same no-item
   policy with an empty bag; adding player-autopilot pill logic is not in this ticket.
4. Apply each candidate action once through `applyBattleCommand`. Score its exact
   damage, kills, facing bonuses, counter losses, qi change and outcome from the
   result's events and state. This is the same reducer path as `forecastMove`; do not
   call both for the same candidate or recreate the damage formula. Count only actor-
   sourced primary damage as offense and actor-targeted damage as counter loss.
5. For each surviving, non-terminal result with the same actor still active, score
   N/E/S/W final facings geometrically. Store the best complete sequence. The chosen
   endTurn must be legal on the speculative result. If the action ends the battle or
   auto-advances after a counter kill, do not append endTurn or plan the next actor.
   For an already-acted input, use the same positioning/facing score with no action.
6. Compare candidates deterministically. From the actor's side, immediate battle
   win ranks above all ongoing choices, and immediate battle loss below them.
   Within each rank compare the numeric score; favor less qi spent, then cheaper
   movement (stay is zero), then destination row z and column x ascending, then
   basic/technique/finisher/Guard/Gather, aim z/x ascending, then current facing
   followed by N/E/S/W. Do not depend on object iteration order or random ties.

Only the winning command list leaves the planner. All other speculative states and
events are discarded. One action and facing enumeration is the ticket's single-turn
evaluation, not a search of later turns or an opponent-response simulation.

## Score

Use one additive score for all archetypes. The following are initial tuning values
in damage-equivalent points; keep values in `content.ts`, not archetype-specific
branches. Use raw actual HP damage and qi amounts (not overkill, hypothetical hits
or fabricated stats). Use integer-scaled weights if useful for stable comparisons.
All figures are provisional until the behavior and full-battle fixtures pass.

| Weight / feature | Aggressor | Marksman | Guardian |
| --- | ---: | ---: | ---: |
| Applied damage per HP | 1 | 1 | 1 |
| Defeated opponents per fighter | 35 | 35 | 35 |
| Weak target per missing health fraction | 12 | 4 | 3 |
| Flank per side/rear step | 3 | 2 | 2 |
| Counter HP lost | -1 | -1.5 | -1.5 |
| Own non-terminal defeat | -100 | -100 | -100 |
| Qi spent per point | -0.10 | -0.10 | -0.10 |
| Qi actually gathered per point | 0.18 | 0.22 | 0.20 |
| Guard with any threatening opponent | 4 | 5 | 14 |
| Ending in bamboo | 1 | 4 | 3 |
| Opponents able to threaten cell | -1 | -4 | -2 |
| Opponents with a rear attack origin | -1 | -2 | -2 |
| Current-position rear/side exposure per step | -1 | -2 | -2 |
| Deviation from preferred range per cell | -4 | -4 | -1 |
| Adjacent hostile per fighter | 0 | -8 | 0 |
| Distance from authored post per cell | 0 | 0 | -5 |
| Preferred range | 1 | 3 | 1 |

- Weak-target bonus uses the pre-hit missing-health fraction, once per living target
  actually hit; flank uses the primary hit's 100/125/150 facingPercent as 0/1/2.
  Count real defeats from primary hit events. Guard bonus is zero when no threat
  exists; Gather uses the actual clamped qi gain from the event.
- Position uses the speculative result after damage/counters: ignore defeated fighters.
  Use Manhattan distance to the nearest living opponent; preferred range is the
  profile's authored distance, capped by the maximum geometrical reach of equipped
  moves (single range, line length, arc maximum Manhattan distance 2), not by
  current qi. Penalize absolute deviation. A Guardian also pays distance from its
  supplied post. For terminal states skip position terms; for a dead non-terminal
  actor apply the defeat penalty and skip position/facing terms.
- Cover is a small incentive for bamboo, not an invented damage reduction. Actual
  mitigation is already in reducer events. Count adjacent living opponents
  using cellDistance.
- Threat is a geometry estimate, not future simulated damage: for each surviving
  hostile in the candidate result, use `getReachableCells(result.state, hostile.id)`
  to get its full movement reach with current occupancy. For each reachable origin
  (including stay), determine whether any affordable owned move could affect the
  actor cell via `legalAimCells` and `affectedCells` (use qi after capped next-turn
  regeneration from INTERNAL_ARTS; no simulated opponent turn). Count each hostile
  at most once, no matter how many moves/origins hit. Obstacles, line/arc patterns,
  weighted terrain and occupied cells must follow existing geometry.
- Rear exposure counts each threatening hostile once for a facing if at least one
  of its attack origins is behind that facing. Also score the hostile's current
  position (front/side/rear = 0/1/2, only for threatening opponents) so all-direction
  threats don't force arbitrary facing. Reuse the current rules' directional
  classification (extract a tiny pure helper if necessary; do not fork its diagonal
  tie behavior). No attack or counter rules are changed.
- Cache geometric attack coverage within a single decision by origin/move and
  threat-origin summaries by candidate cell plus surviving fighter IDs/positions
  (and affordable-move set if relevant). Reuse the summary for four facings and
  actions sharing that geometry. Never keep state across decisions. Start with
  straightforward short-circuiting and add only the local caching necessary to
  hit the frame budget. Enumerate every legal candidate; no hard-coded top-N pruning.

Manhattan range/post preferences are deliberately simple. A local policy can stall
on unreachable terrain or pathological layouts; no universal termination or
perfect tactical play is promised. Test reachable authored layouts (including a
short obstacle detour where progress is possible). If a representative fixture
stalls, tune range/Guard/Gather weights or use existing weighted grid distances
as a spatial approach tie-break, not a multi-turn tactical search. Do not add a
round cap or forced battle outcome to production rules.

## Verification

Pure Node/Vitest tests cover each archetype, all legal action/position candidates,
deterministic tie order, phase handling, no mutation, guard/counter/terminal and
auto-handoff behavior, terrain and range, and facing/threat estimates. A public-API
AI-vs-AI journey on a reachable authored map must reach a real terminal outcome
under a bounded test turn count; replay from fresh and JSON-round-tripped states
must yield the same commands, events and terminal state. Test both sides with empty
bags and assert every returned command is accepted.

Measure warmed decision latency on a 16 x 16, twelve-living-fighter representative
mixed-terrain fixture with an active actor in range of multiple enemies and normal
starter movement budgets. Target p95 <= 16.7 ms (one 60 Hz frame); record runtime,
hardware, iteration count and p95/max, do not assert noisy wall-clock timing in CI.
Measure through execution MCP; if the budget is missed, optimize and rerun before
claiming acceptance. No performance claims are made by this design-only PR.

No UI or mockup for HPA-1311. Inspect the existing exploration screenshot from
the full Playwright regression (MCP/artifact viewer) for unchanged village HUD,
canvas, quest and minimap; do not create a new AI UI or require a manual visual
sign-off. See the implementation plan for the exact acceptance checklist.
