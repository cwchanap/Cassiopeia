# HPA-1311 — Enemy AI for Turn-Based Battles (Design Spec)

**Linear:** [HPA-1311](https://linear.app/cwchanap/issue/HPA-1311/enemy-ai-for-turn-based-battles)  
**Base:** `main` at `cf7c52942251e2046d3d926c03e406d76d3ad98b` (HPA-1310 / PR #6 merged).  
**Delivery:** One draft PR for design, implementation, tests and acceptance evidence.

## Goal and boundaries

Give a computer-controlled fighter one deterministic turn of legal battle commands. Three
data-defined archetypes ship: Aggressor closes and targets the weakest opponent it can
profitably hit; Marksman prefers standoff distance and avoids adjacent opponents; Guardian
stays near an encounter-authored post, Guards frequently and punishes approaching opponents.
The same planner can control the squad in a headless integration test.

The battle engine remains the sole rules authority. No live game integration, renderer,
HUD, animation, save change, encounter content, art, audio, difficulty, tactical lookahead
or per-encounter scripts. HPA-1315 owns the playable spar and its runtime scheduling.
Do not add an AI framework, a dependency, a separate battle-state model or an asynchronous
worker. Do not redesign the existing reducer.

## Current code and public contract

`src/lib/game/simulation/battle/index.ts` already exports `createBattle`,
`getTurnOrder`, `getReachableCells`, `getMoveTargets`, `applyBattleCommand`,
`forecastMove`, `legalAimCells`, `affectedCells`, `cellDistance` and the
catalogs. `BattleState` contains `hasMoved`, `hasActed`, `outcome`, initiative,
fighters and terrain. Commands return a fresh state and ordered events on acceptance.

Add `ai.ts` (planner and score helpers), extend `content.ts` with the named readonly
weight catalogs below, and add these public contracts to `types.ts`/the barrel:

```ts
type AiArchetypeId = 'aggressor' | 'marksman' | 'guardian';
type BattleAiProfile =
	| { archetype: 'aggressor' | 'marksman' }
	| { archetype: 'guardian'; post: Cell };

function planBattleTurn(
	state: BattleState,
	actorId: string,
	profile: BattleAiProfile
): BattleCommand[];
```

The caller owns profile assignment; do not put AI configuration in BattleState,
FighterTemplate or the save. Validate the authored profile **first**, even for terminal
battles or inactive/unknown actors: reject a missing profile or an archetype outside the
three closed IDs (use an own-key membership check or explicit IDs). A Guardian must have
a non-null post with integer x/z that is standable on this map; reuse
`canEnterTerrain(terrainAt(map, post))` after the presence check (terrainAt validates
integer bounds). Missing, fractional, out-of-bounds, obstacle and water posts throw a
clear authored-configuration error; ground and bamboo are valid regardless of current
occupancy. Do not silently invent a post. This is a small configuration guard, not a
general state schema validator. Only after successful validation, return an empty
array for terminal state, a dead/unknown actor or a non-active actor. Either side may
be AI-controlled. A normal result
contains optional move, one action and endTurn with final facing, except when the
action itself ends the battle or kills the actor and hands off. A partially completed
active turn is supported: after movement, omit movement; after action, only choose
endTurn. The input state and profile must remain unchanged, and returned commands must
own their coordinates rather than aliasing the input. No mutation, wall clock or
randomness in the planner. It returns commands, not events or a new authoritative state.

A future runtime can either replay the returned sequence through the reducer or call
`planBattleTurn(state, actorId, profile)[0]` at each command boundary while that
fighter remains active. The actor-excluded threat geometry is unchanged by that
actor's move alone, though replanning after an action can reflect casualties and
need not reproduce a previously planned suffix. HPA-1315 owns that
choice and event playback. No queue, invalidation protocol or scheduler is added here.

## Enumerating a turn

1. Validate the profile as above, then check `getTurnOrder(state).activeId` and outcome.
   Include the current cell once (no move command); enumerate every other legal cell
   from `getReachableCells(state)` without an explicit fighter ID. The explicit-ID
   overload also includes the active actor as a blocker, so it is not used for the
   threat map; see the separate approximate geometry below.
2. For each cell, apply the actual move command once to obtain a speculative state, or
   use the input state for staying. Scan destinations in the query's stable cost/discovery
   order (stay first). Never relocate fighters by writing into a shallow
   copy or recompute path costs. Rejecting an allegedly legal move is a regression, not
   an alternative rules path.
3. In that state, enumerate all owned move slots in basic/technique/finisher order.
   `getMoveTargets` already filters ownership, qi and valid aims with living hostile
   targets, including line/arc multi-target hits. Consider every returned aim, plus
   Guard and Gather qi even at full qi (legal but gains zero). Enemy fighters cannot
   use the shared squad bag. For the squad-side test controller use the same no-item
   policy with an empty bag; adding player-autopilot pill logic is not in this ticket.
4. Apply each candidate action once through `applyBattleCommand`. Extract the existing
   accepted-attack projection in `forecastMove` into a module-internal
   `summarizeAttack(result, actorId)` helper in `rules.ts` (importable within battle,
   not exported from the public barrel). Both forecastMove and the AI call it with
   the accepted useMove result. Reuse the original actor's qi/health, primary hits,
   counters, defeats, outcome and handoff; do not accidentally read the next
   actor's regeneration or parse attack events twice. Guard and Gather use their
   own accepted action result and Gather's actual qi event. No duplicate reducer
   call, damage formula or attack event parser; existing forecast tests must pass.
5. For each surviving, non-terminal result with the same actor still active, score
   all four final facings geometrically, current facing first then N/E/S/W (omit
   duplicate current facing). Store the best complete sequence. The chosen
   endTurn must be legal on the speculative result. If the action ends the battle or
   auto-advances after a counter kill, do not append endTurn or plan the next actor.
   For an already-acted input, use the same positioning/facing score with no action.
6. Compare candidates by terminal rank (actor-side win > ongoing > actor-side
   loss), then integer score, then first encountered. Stay first, reachable cells
   in existing cost/discovery order, owned moves in slot order and their aims
   in existing query order, then Guard, Gather; current facing before remaining
   N/E/S/W. Replace the incumbent only on strictly better rank/score. This is
   a stable scan order, not an additional global qi or coordinate sort. A lower
   qi action is naturally visited first at the same destination for starter arts.
   No reliance on incidental object iteration order or random ties.

Only the winning command list leaves the planner. All other speculative states and
events are discarded. One action and facing enumeration is the ticket's single-turn
evaluation, not a search of later turns or an opponent-response simulation.

## Score

Use one additive integer score for all archetypes. One damage-equivalent point
is 100 score units. All feature values and weights are integers, including a
rounded weak-target bonus; do not compare floating-point totals. Use actual applied
HP/qi (not overkill). Keep shared weights and the small per-archetype record
together in `content.ts`, frozen by its existing deepFreeze helper. These are
initial values; tune against the early journey and behavior tests.

Public data contract: export `AiArchetypeWeights` from `types.ts` with readonly
numeric fields `weakTarget`, `flank`, `counterLoss`, `gatherQi`, `guard`, `bamboo`,
`threatCount`, `rearThreat`, `currentExposure`, `rangeDeviation`, `adjacentHostile`,
`postDistance` and `preferredRange` (cells). Export `AI_SHARED_WEIGHTS` (readonly
`damage`, `defeat`, `selfDefeat`, `qiSpent`) and
`AI_ARCHETYPES: Readonly<Record<AiArchetypeId, AiArchetypeWeights>>` from `content.ts`;
both are deep-frozen. These names are public through the existing barrel star
exports. Reuse the existing deepFreeze helper; no extra catalog or public scorer.

Shared weights: applied primary damage +100 per HP; opponent defeat +3500 per
fighter; own non-terminal defeat -10000; qi spent -10 per point.

| Weight / feature                              | Aggressor | Marksman | Guardian |
| --------------------------------------------- | --------: | -------: | -------: |
| Weak target at 100% missing HP (scaled below) |      1200 |      400 |      300 |
| Flank per side/rear step                      |       300 |      200 |      200 |
| Counter HP lost                               |       -50 |     -150 |     -150 |
| Qi actually gathered per point                |        18 |       22 |       20 |
| Guard with any threatening opponent           |         0 |      500 |      600 |
| Ending in bamboo                              |       100 |      400 |      300 |
| Opponents able to threaten cell               |      -100 |     -400 |     -200 |
| Opponents with a rear attack origin           |      -100 |     -200 |     -200 |
| Current-position rear/side exposure per step  |      -100 |     -200 |     -200 |
| Deviation from preferred range per cell       |      -400 |     -400 |     -100 |
| Adjacent hostile per fighter                  |         0 |     -800 |        0 |
| Distance from authored post per cell          |         0 |        0 |     -500 |
| Preferred range (cells, not score)            |         1 |        3 |        1 |

- For each primary hit, round the weak-target bonus down once:
  `Math.floor(weight * (maxHealth - healthBefore) / maxHealth)`, using the
  target's pre-hit maxHealth. Flank uses the hit's 100/125/150 facingPercent
  as 0/1/2. Count defeats from the shared attack summary; counter HP loss
  is actual applied counter damage. Guard gets zero bonus without a threat,
  and Gather uses actual clamped qi gain. Aggressor has no positive Guard bonus
  and a lower counter penalty to favor dealing damage instead of mutual Guard;
  Guard remains a legal candidate (zero bonus does not forbid selecting it).
  Guardian starts with a smaller positive bonus so clean hits can beat guarding.
- Position uses the speculative result after damage/counters: ignore defeated fighters.
  Use Manhattan distance to the nearest living opponent; preferred range is the
  archetype catalog's preferred distance, capped by the maximum geometrical reach of equipped
  moves (single range, line length, arc maximum Manhattan distance 2), not by
  current qi. Penalize absolute deviation. A Guardian also pays distance from its
  supplied post. For terminal states skip position terms; for a dead non-terminal
  actor apply the defeat penalty and skip position/facing terms.
- Cover is a small incentive for bamboo, not an invented damage reduction. Actual
  mitigation is already in reducer events. Count adjacent living opponents
  using cellDistance.
- Build one actor-excluded threat map per decision, before scanning destinations:
  `Map<hostileId, Map<cellKey, Cell[]>>`, mapping each hostile and threatened
  cell to unique reachable attack-origin cells. For every living hostile use
  `computeReachableCells(state.map, hostile.cell, movementBudget(hostile), occupied)`
  from the existing grid/rules modules; `occupied` contains every living fighter's
  cell **except the hostile and the acting fighter**. Export the existing
  `movementBudget(fighter)` within the battle module, not from the public barrel,
  without changing its formula or the real move legality query. Never use
  `getReachableCells(state, hostile.id)` here: it treats the acting fighter's
  original cell as a blocker, even for candidates that vacate it.
  Enumerate owned moves affordable after capped next-turn regeneration (INTERNAL_ARTS),
  `legalAimCells` and `affectedCells` from each reachable origin (including stay);
  record each origin once per cell, regardless of how many moves/aims hit.
  Use existing weighted terrain, remaining occupancy, obstacle and move-shape rules.
  This is a geometric estimate, not a forecast of future damage.
- Score candidate position using the map lookup for the actor's final cell,
  excluding hostiles killed by that candidate. Count distinct surviving
  threatening hostiles once; count each once for rear exposure if any recorded
  attack origin is behind the chosen facing. Score each threatening hostile's
  current position as front/side/rear 0/1/2 too. Share the exact classification
  currently in `facingPercentFor` by extracting a small module-internal helper in
  `rules.ts` taking target cell, facing and attacker cell; preserve diagonal ties
  and all damage semantics. Keep damage percentages out of rule-independent
  `grid.ts`. All four facings reuse the same threat map.
- Documented approximation: the actor is omitted from blockers for **all**
  candidates, including stay, so no starting-cell ghost shielding or stay bias.
  A hostile path may pass through the hypothetical occupied destination, and a
  subsequently defeated non-actor fighter may still block paths in the estimate.
  Exclude killed hostiles from lookup; do not recompute their neighbors' paths.
  Thus threats can be over- or underestimated, but the geometry is symmetric
  with respect to the actor's destinations and invariant to its move alone.
  Actual candidate movement, attacks, counters and outcomes use the exact
  reducer. Do not recompute hostile pathfinding per candidate, build a cache
  keyed by destination, persist a map across turns, or prune candidates.
  The map is local to one decision.
- Regression fixture: open ground, hostile agility 10 (budget 3) with
  Sect Sword at (2,2), actor Marksman at (3,2). The map must register the
  hostile's origin (5,2) threatening (6,2) via Sword Cut; a retreat cannot
  gain false safety from the actor's vacated (3,2). Compare map contents
  for this actor before and after its legal move alone (same other fighters,
  terrain, qi and stats), and check stay and lateral destinations use the
  same actor-excluded occupancy. Other living fighters still block paths.

Manhattan range/post preferences are deliberately simple. A local policy can stall
on disconnected or pathological layouts; no universal termination is promised.
Build the public-API battle loop before final scoring, and keep two mutual-reach
Lu/hero fixtures (Aggressor hero against Aggressor Lu and against Guardian Lu at
his post) in the tuning loop. Use actual starter stats, full health/qi, opposing
facing and empty bags; require at least one actual HP reduction by the end of
round 4 and a genuine terminal outcome within 200 planned turns in both.
Also test a mixed-archetype battle and a reachable short obstacle detour. A
zero-Gather/Guard loop or indefinite standoff fails the fixtures. Tune scores
first; add only a simple spatial approach tie-break if demonstrated necessary,
without introducing tactical lookahead. Do not add a production round cap,
forced outcome, scripted player commands or artificially depleted HP to pass.

## Verification

Pure Node/Vitest tests cover each archetype, all legal action/position candidates,
deterministic tie order, phase handling, no mutation, guard/counter/terminal and
auto-handoff behavior, terrain and range, and facing/threat estimates. A public-API
AI-vs-AI journey on a reachable authored map must reach a real terminal outcome
under a bounded test turn count; build that test early and use it while tuning.
The two mutual-reach spar fixtures must also pass. Replay the mixed battle from
fresh and JSON-round-tripped states and require it to yield the same commands, events and terminal state. Test both sides with empty
bags and assert every returned command is accepted.

Use one representative 16 x 16 mixed-terrain benchmark (six fighters per side,
active Willow Darts fighter with movement budget 5, several enemies/Guard threats
in potential reach). All archetypes share the same candidate scan. In
`ai.perf.spec.ts`, include a fast always-on single-decision legality test with
assertions and gate the actual timing test using
`it.runIf(process.env.RUN_AI_BENCH === '1')`. Normal Vitest runs discover this
file and require assertions, but must not run timed iterations or timing assertions.
Run once after full scoring via execution MCP:

```sh
RUN_AI_BENCH=1 bun x vitest run src/lib/game/simulation/battle/ai.perf.spec.ts
```

Warm up 30 decisions, collect at least 50 timed decisions, report median/p95/max,
host, runtime, fixture and candidate/reachable-cell count. Assert warmed
p95 <= 16.7 ms (60 Hz) in the explicitly opted-in test only. Validate command
legality outside timing. The reviewer reported about 122 ms median for the
original per-candidate threat loop and 3.7 ms for a single-map prototype plus
enumeration on an M1 Pro scratch fixture; these are reviewer measurements,
not verified implementation results. Measure the actual implementation before
claiming acceptance; profile if it misses the target.

No UI or mockup for HPA-1311. Verify the final diff is limited to battle/, CLAUDE.md
and the planning docs. Reuse the existing exploration screenshot from the full
Playwright regression or its CI artifact (MCP/artifact viewer) for unchanged
village HUD, canvas, quest and minimap; no separate browser run, new AI UI or
human sign-off. See the implementation plan for the exact acceptance checklist.
